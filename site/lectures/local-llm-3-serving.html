Сервер моделей: как обслужить много запросов и получить ответ по схеме

Лекции 1 и 2 отвечали, какая модель влезет в какое железо и как быстро она печатает. Эта лекция отвечает, как превратить модель на карте в сервис: сколько запросов карта держит одновременно, какие флаги ставить, как получить ответ строго по JSON-схеме и как замерить скорость. Примеры проверены на Mac из примера 12 и 14.10.2026.

Коротко: вся лекция за две минуты
  1. Сервер моделей держит модель в памяти и отвечает по HTTP. Почти все серверы говорят на языке OpenAI API, поэтому код клиента один на Ollama и vLLM. 02
  2. Ollama - для одной машины и одного пользователя, vLLM - для потока запросов на картах NVIDIA. 03
  3. KV-кэш на токен считается по config.json: 2 * слои * KV-головы * размер головы * байт на число. Он решает, сколько запросов влезет в карту. 04
  4. Непрерывный батчинг читает веса один раз на все запросы. Суммарная скорость карты растёт в разы, скорость одного запроса падает. 05
  5. Общий начальный текст промпта сервер считает один раз. Чек-лист в начале промпта ускоряет prefill всех звонков. 06
  6. Для оценки по критериям: низкая температура, фиксированный seed, режим рассуждения выключен до замера, ответ по JSON-схеме. 08 09
  7. Скорость меряют четырьмя числами: время до первого токена, время на токен, суммарные токены в секунду и задержка 99% запросов. 10
  8. Спекулятивное декодирование угадывает несколько токенов вперёд и проверяет их за одно чтение весов. Так скорость обходит потолок из лекции 2. 11

Учебная версия для публичной библиотеки. Рабочие сведения исключены, примеры обобщены. Версии и измерения сохранены на дату исходной лекции.

Проверь себя: почему Q8 на Mac из примера печатает медленнее Q4 той же модели?

На каждый токен модель читает из памяти все веса. Файл Q8 в 1,6 раза больше, поэтому при тех же 120 ГБ/с токенов в секунду меньше.

Проверь себя: что дала карта A100 FP8-модели и чего не дала?

Веса стали вдвое меньше, и генерация ускорилась. Аппаратного FP8 у Ampere нет, поэтому prefill считается в 16 битах.

02

Сервер моделей

Что это

Сервер моделей (inference server) - это программа, которая держит модель в памяти карты и отвечает на запросы по HTTP. Проще говоря, это веб-сервер, у которого вместо базы данных нейросеть. Сервер принимает запрос, ставит его в очередь, планировщик собирает из очереди пачку (батч), карта считает prefill и генерацию, а токены уходят клиенту потоком (рис. 1).

OpenAI-совместимый API

OpenAI-совместимый API - это набор адресов и полей запроса, как у сервиса OpenAI: /v1/chat/completions, поле messages, поле response_format. Его понимают Ollama, llama.cpp, LM Studio, vLLM и SGLang910. Поэтому код клиента пишется один раз: при переходе с Ollama на маке на vLLM на сервере меняется только адрес.

# один клиент на любой сервер: меняется только base_url
from openai import OpenAI
client = OpenAI(base_url="http://localhost:11434/v1", api_key="ollama")   # Ollama на маке
# client = OpenAI(base_url="http://gpu-server:8000/v1", api_key="...")   # vLLM на сервере

Совместимость неполная. Через OpenAI API Ollama не принимает tool_choice (выбор инструмента), logprobs (вероятности токенов) и n (несколько вариантов ответа). Длину контекста там задать нельзя: только через свой API или Modelfile - файл настроек модели в Ollama9.

ВыводСервер моделей - это очередь, планировщик и модель на карте за HTTP-адресом. Клиент пишут под OpenAI API и не привязывают к серверу.
03

Движки

Движок (inference engine) - это программа, которая выполняет модель на железе. Сервер моделей принимает запросы по HTTP, а движок их выполняет; у Ollama, llama-server и vLLM обе роли собраны в одной программе. Шесть движков покрывают почти все случаи (табл. 2).

Ollama

Ollama - это обёртка над llama.cpp, которая сама скачивает модели и держит их в памяти. С версии 0.40 на Apple Silicon она работает через MLX28. Её слабое место - параллельность: по умолчанию одна модель обслуживает один запрос, остальные ждут в очереди до 512 запросов, дальше сервер отвечает ошибкой 5037.

vLLM

vLLM - это сервер для карт, который держит десятки и сотни одновременных запросов. Он выдаёт KV-кэш блоками по мере надобности (раздел 04) и собирает запросы в непрерывный батч (раздел 05). Цена - он работает с весами в safetensors и требует настройки флагов под карту.

GGUF из Ollama не всегда открывается в llama.cppФайл qwen3.5:4b из папки Ollama llama.cpp сборки 11429 на Mac из примера не загрузил: «key qwen35.rope.dimension_sections has wrong array length». Ollama собирает GGUF по-своему, для llama.cpp бери файл с Hugging Face.
Документация Ollama расходитсяFAQ пишет контекст по умолчанию 4096, страница о контексте - 4k до 24 ГиБ памяти, 32k до 48 ГиБ и 256k выше78. Проверяй командой ollama ps.

04

KV-кэш

Что это

KV-кэш (KV cache) - это память, где модель хранит ключи и значения всех уже прочитанных токенов запроса. Проще говоря, это рабочая память контекста: без неё модель на каждый новый токен перечитывала бы весь вход заново. Каждый слой внимания добавляет в кэш два вектора на токен, поэтому кэш растёт с длиной запроса и с числом одновременных запросов. Он решает, сколько запросов влезет в карту.

Формула

Размер кэша на один токен считается по трём полям config.json из лекции 1:

KV на токен = 2 * слои * KV-головы * размер головы * байт на число

T-pro-it-2.1:  2 * 64 * 8 * 128 * 2 байта = 262 144 байта = 256 КиБ
запрос 8 тыс. токенов:  8192 * 256 КиБ = 2 ГиБ

Qwen3.6-27B:   2 * 16 * 4 * 256 * 2 байта = 65 536 байт = 64 КиБ
запрос 8 тыс. токенов:  8192 * 64 КиБ = 0,5 ГиБ

Двойка в начале - это ключ и значение. У Qwen3.6-27B полное внимание стоит только в 16 слоях из 64, остальные слои линейные и хранят состояние постоянного размера26. Поэтому её кэш на токен вчетверо меньше, чем у T-pro25.

Бюджет карты

vLLM по умолчанию забирает 92% памяти карты (--gpu-memory-utilization 0.92)1. Из них вычитаются веса и служебный запас около 4 ГиБ (допущение). Остаток уходит под KV-кэш, и он задаёт, сколько запросов карта держит одновременно (рис. 2).

Как читать

  1. Синяя часть - веса, она одинакова при любой нагрузке.
  2. Зелёная часть - KV-кэш, её делят все одновременные запросы.
  3. T-pro на 48 ГБ помещается, но на KV-кэш остаётся 6 ГиБ, это 3 запроса по 8 тыс. токенов.
  4. С --kv-cache-dtype fp8 кэш занимает 1 байт на число вместо 2, и число запросов удваивается1.

PagedAttention

PagedAttention - это способ хранить KV-кэш блоками фиксированной длины, как страницы памяти в операционной системе. Старые серверы резервировали под каждый запрос место на максимальную длину и теряли на этом 60-80% памяти. vLLM выдаёт блоки по мере роста запроса и ведёт таблицу блоков, потери падают ниже 4%3 (рис. 3). В ту же память влезает больше одновременных запросов, и по замерам авторов пропускная способность сервера выросла в 2-4 раза4.

Считать только весаМодель на 31 ГиБ «влезает» в 48 ГБ, но на параллельные запросы памяти не остаётся.
Контекст на всякий случай--max-model-len ставь по реальной длине звонка с запасом, а не по максимуму из карточки.
ГБ и ГиБ1 ГиБ = 1,074 ГБ. На 96 ГБ разница уже 6 ГиБ, этого хватит на 3 запроса T-pro.

05

Параллельные запросы

Непрерывный батчинг

Непрерывный батчинг (continuous batching) - это режим, в котором сервер на каждом шаге генерирует по токену сразу для всех активных запросов. Проще говоря, веса читаются из памяти один раз, а токен получают тридцать запросов. Закончившийся запрос уходит из батча сразу, а ждущий занимает его место на следующем шаге, без ожидания остальных11 (рис. 4).

Что это даёт на карте

Суммарная скорость карты растёт с числом параллельных запросов, а скорость одного запроса падает. Замер на RTX PRO 6000 показывает это на модели Qwen3-32B (рис. 5).

Как читать

  1. Синяя линия FP8 везде выше коричневой BF16: меньше байт на чтение, больше токенов.
  2. От 8 до 128 запросов суммарная скорость FP8 выросла в 5,4 раза.
  3. Скорость одного запроса при этом упала: 36 ток/с при 8 запросах и 12 при 128 (расчёт).

Ollama и vLLM под нагрузкой

Red Hat сравнил оба сервера на A100 40 ГБ с Llama 3.1 8B при 1-256 одновременных запросах. vLLM дошёл до 793 ток/с суммарно, Ollama - до 41 ток/с. Задержка между токенами у 99% запросов составила 80 мс у vLLM и 673 мс у Ollama. С OLLAMA_NUM_PARALLEL=32 суммарная скорость Ollama перестала расти, а задержка между токенами стала скакать12. Замер 2025 года, свежее независимого сравнения разведка не нашла.

Тот же эффект виден на Mac из примера. Четыре запроса к Ollama с настройками по умолчанию ушли одновременно, а закончились по очереди (раздел 13, упражнение 2):

запросов 1: готовы через, с: [4.4]; токенов 100; суммарно 22.6 ток/с
запросов 4: готовы через, с: [4.0, 7.8, 11.7, 15.6]; токенов 400; суммарно 25.6 ток/с

Из вывода видно, что суммарная скорость не выросла, а последний запрос ждал вчетверо дольше первого. Это очередь из верхней половины рисунка 4.

Вспомни лекцию 2

Таблица 10 лекции 2 считала потолок одного запроса: 64 ток/с для Qwen3.6-27B на RTX PRO 6000. С батчингом карта выдаёт в разы больше суммарно, а каждый запрос получает меньше 64.

06

Кэш префикса

Кэш префикса (prefix caching) - это режим, в котором сервер хранит KV-кэш начала промпта и переиспользует его в следующих запросах с тем же началом. Проще говоря, общий текст считается один раз. vLLM делит промпт на блоки, считает хеш каждого блока вместе с хешем предыдущего и находит готовые блоки по хешу; старые блоки вытесняются по давности использования5.

Кэш префикса ускоряет prefill, а не генерацию. В vLLM он включён по умолчанию: в исходниках enable_prefix_caching: bool = True6. Флаг --enable-prefix-caching из старых инструкций больше не нужен.

Что это значит для звонков

Чек-лист и инструкция одинаковы для всех звонков, а расшифровка у каждого своя. Поэтому порядок частей промпта решает, сработает ли кэш:

Правильно:

[инструкция + чек-лист, общие для всех звонков] [расшифровка звонка]

Общий блок одинаков в начале каждого запроса, сервер считает его KV-кэш один раз.

Неправильно:

[расшифровка звонка] [инструкция + чек-лист]

Начало у каждого звонка своё, поэтому хеш первого блока не совпадает, и кэш не срабатывает даже для одинакового чек-листа.

Хеш блока зависит от всех предыдущих токенов. Если начало промпта отличается хоть одним токеном, например датой или номером звонка, кэш всех следующих блоков не найдётся.

ВыводОбщий текст промпта ставь в начало и не меняй его между запросами: сервер посчитает его один раз.

07

Запуск сервера

vLLM

Команда ниже поднимает T-pro-it-2.1 в FP8 с OpenAI-совместимым API на порту 8000. Значения флагов - стартовые для условной задачи обработки текста, их уточняет пилот.

vllm serve t-tech/T-pro-it-2.1-FP8 \
  --max-model-len 16384 \
  --gpu-memory-utilization 0.92 \
  --kv-cache-dtype fp8 \
  --max-num-seqs 32

Что делает каждый флаг:

  1. --max-model-len 16384 ограничивает контекст одного запроса. Звонок с чек-листом и ответом занимает до 8 тыс. токенов, остальное - запас.
  2. --gpu-memory-utilization 0.92 отдаёт vLLM 92% памяти карты, это значение по умолчанию1.
  3. --kv-cache-dtype fp8 хранит KV-кэш в 1 байте на число и вдвое увеличивает число одновременных запросов. Есть также nvfp4 для Blackwell1.
  4. --max-num-seqs 32 пускает в батч не больше 32 запросов. Документация не называет значение по умолчанию, поэтому его задают явно. Число 32 взято вдвое выше 16 звонков из расчёта лекции 2: на карте 96 ГБ с KV в FP8 у T-pro 47 ГиБ кэша хватает примерно на 47 запросов по 8 тыс. токенов (рис. 2).

Для моделей Qwen с режимом рассуждения добавь --reasoning-parser qwen3: без него рассуждение смешается с ответом, а ответ по схеме может отключиться1416.

llama.cpp

llama-server поднимает тот же OpenAI API для GGUF-файла, непрерывный батчинг в нём включён по умолчанию10. Слот (slot) - это место для одного одновременного запроса: флаг -np задаёт число слотов, флаг -c - общий контекст на все слоты.

# 4 слота делят 32768 токенов контекста: по 8192 на запрос
llama-server -m Qwen3.8-27B-Q4_K_M.gguf -c 32768 -np 4 --port 8080

Деление проверено на Mac из примера: сервер с -c 4096 -np 4 напечатал n_slots = 4, n_ctx_slot = 102434.

Ollama

Ollama настраивают переменными окружения сервера: OLLAMA_NUM_PARALLEL - число одновременных запросов на модель, OLLAMA_KV_CACHE_TYPE=q8_0 - KV-кэш в 8 битах. Память растёт пропорционально числу параллельных запросов, умноженному на контекст7.

Две модели на одной карте

Один процесс vLLM обслуживает одну модель. Для двух моделей нужно два процесса, каждому своя доля памяти, например по 0,45. На форуме vLLM пишут, что второй процесс на той же карте часто не стартует35. Надёжнее две карты или модели по очереди.

Параметры генерации

Параметры генерации (sampling parameters) - это настройки, с которыми модель выбирает следующий токен (табл. 3). На каждом шаге модель выдаёт вероятности всех токенов словаря, а параметры решают, как из них выбрать один. Пример с условными числами: после слова «Добрый» модель даёт «день» 0,7, «вечер» 0,2, «утро» 0,1. При temperature 0 она всегда выберет «день». При top_p 0,8 она выбирает только из «день» и «вечер»: их сумма первой дошла до 0,8. Их передают в каждом запросе, а значения по умолчанию vLLM берёт из файла generation_config.json модели1.

Режим рассуждения

Режим рассуждения (thinking) - это режим, в котором модель сначала пишет скрытое рассуждение, а потом ответ. Он тратит токены и время, а качество на простых критериях может не вырасти. У Qwen3.8-27B по карточке уровень рассуждения по умолчанию xhigh19. Каждый сервер выключает его по-своему (табл. 5).

Ответ по схеме

Как это работает

Структурированный вывод (structured output) - это режим, в котором сервер разрешает модели только токены, подходящие под JSON-схему. На каждом шаге сервер по схеме вычисляет, какие токены допустимы дальше, и обнуляет вероятность остальных. Поэтому модель физически не может вернуть лишнее поле или значение вне списка. В vLLM эту работу делают бэкенды - библиотеки, которые переводят схему в правила выбора токенов: xgrammar или guidance, по умолчанию выбор автоматический14.

Минимальный пример

Схему удобно описать моделью Pydantic, а клиент openai передаст её в поле response_format. Код ниже работает и с Ollama, и с vLLM:

from typing import Literal
from pydantic import BaseModel

class Verdict(BaseModel):                                   # схема ответа
    criterion: str
    answer: Literal["yes", "no", "partial", "na"]          # только эти четыре значения
    quote: str                                              # цитата из расшифровки
    utterance: int                                          # номер реплики

resp = client.chat.completions.create(
    model="qwen3.5:4b",
    temperature=0, seed=42,                                 # повторяемость
    reasoning_effort="none",                                # без рассуждения
    response_format={"type": "json_schema",
                     "json_schema": {"name": "verdict", "schema": Verdict.model_json_schema()}},
    messages=[{"role": "user", "content": prompt}],
)
verdict = Verdict.model_validate_json(resp.choices[0].message.content)  # проверка в коде

Настоящий ответ Ollama на Mac из примера на синтетический звонок 14.10.202634:

{
  "criterion": "оператор поздоровался и назвал компанию",
  "answer": "yes",
  "quote": "Добрый день, компания Ромашка, меня зовут Анна.",
  "utterance": 1
}
prompt_tokens 85 completion_tokens 61 seconds 7.2

Из вывода видно, что ответ прошёл проверку Pydantic, а цитата взята из реплики 1 дословно. 7,2 с включают загрузку модели в память: это был первый запрос после паузы. Схема гарантирует форму ответа, но не правильность: цитату код всё равно сверяет с расшифровкой.

Ограничения

  1. Старые параметры vLLM guided_json и guided_decoding_backend удалены в версии 0.12.0: инструкции с ними устарели14.
  2. С моделью-рассуждателем vLLM нужен --reasoning-parser, иначе схема может не применяться к ответу14.
  3. Документация vLLM и Ollama советует продублировать схему словами в промпте: модель с понятной задачей реже упирается в ограничения15.

Замер скорости

Четыре метрики

Скорость сервера описывают четыре числа:

  1. TTFT (time to first token): время от запроса до первого токена. Это prefill плюс ожидание в очереди.
  2. TPOT (time per output token): среднее время на один токен ответа после первого. Это генерация.
  3. Throughput: суммарные токены в секунду по всем запросам. Это то, что растёт от батчинга.
  4. ITL (inter-token latency): время между соседними токенами одного ответа, по смыслу близко к TPOT.
  5. P99: значение, которое не превышают 99% запросов. Оно показывает самые медленные запросы, которые среднее значение прячет.

TPOT считается так: время всего запроса минус TTFT, делённое на число токенов ответа минус один20.

vllm bench serve

vllm bench serve - встроенный инструмент vLLM, который шлёт на запущенный сервер поток запросов и печатает метрики. Для условной задачи обработки текста профиль запроса стоит взять как у звонка:

vllm bench serve \
  --model t-tech/T-pro-it-2.1-FP8 \
  --dataset-name random \
  --random-input-len 6000 \
  --random-output-len 1000 \
  --num-prompts 200 \
  --max-concurrency 16 \
  --percentile-metrics ttft,tpot,itl \
  --metric-percentiles 99

Длины входа и выхода здесь - оценка по звонку на 6 тыс. токенов и ответу до тысячи, их уточняют по реальным расшифровкам. Пример вывода из документации vLLM на 10 запросах к модели 8B21:

Output token throughput (tok/s):   382.89
Mean TTFT (ms):                    71.54
Mean TPOT (ms):                    7.91
Mean ITL (ms):                     7.74

Из вывода видно, что один токен уходил за 8 мс, то есть около 126 ток/с на запрос. Первый токен пришёл через 72 мс. Пример запускали без процентилей, поэтому строк P99 в нём нет; с флагом --metric-percentiles 99 vLLM добавит их к каждой метрике.

Ollama и llama.cpp

У Ollama своего бенчмарка нет. Флаг --verbose печатает скорость одного запроса: prompt eval rate - это prefill, eval rate - генерация (лекция 1, раздел 15). У llama.cpp есть llama-bench: команда llama-bench -m model.gguf -p 1024 -n 128 печатает скорость prefill (pp, prompt processing) и генерации (tg, text generation)22. По ней собраны таблицы карт в лекции 2.

Спекулятивное декодирование

Спекулятивное декодирование (speculative decoding) - это приём, при котором быстрый помощник угадывает несколько следующих токенов, а большая модель проверяет их все за одно чтение весов. Проще говоря, модель не пишет каждое слово сама, а проверяет черновик. Угаданные токены принимаются, на первом неугаданном модель ставит свой токен, и шаг повторяется (рис. 6).

Виды помощников

  1. Draft model: помощником работает отдельная маленькая модель того же семейства.
  2. EAGLE: помощником работает небольшой дополнительный слой поверх большой модели, обученный угадывать следующие токены.
  3. MTP (multi-token prediction): модель обучена сама предсказывать несколько токенов вперёд, помощник встроен в неё.
  4. N-gram: помощник угадывает по повторам текста из промпта, без модели.

vLLM поддерживает все эти виды через флаг --speculative-config, llama.cpp - через --spec-type2310. Приём сокращает задержку между токенами, когда генерация упирается в память и запросов немного. При большом батче карта и так загружена, и выигрыш меньше.

Вспомни лекцию 2

Замер Qwen3.6-27B на RTX PRO 6000 дал 97,5 ток/с в FP8 при потолке 64 из таблицы 10 лекции 2. Автор включил MTP с двумя токенами вперёд и не больше двух запросов одновременно24. Формула потолка считает одно чтение весов на токен, а здесь одно чтение даёт несколько токенов.

Проверка качества

Скорость меряет инструмент из раздела 10. Качество оценки звонков меряют сравнением с человеком: эталон - ручная оценка руководителя по тем же критериям. Порядок проверки модели такой:

  1. Отсеять модели по лицензии, языку и памяти (лекция 1, раздел 14; лекция 2, раздел 11).
  2. Собрать золотой набор - звонки с эталонной ручной оценкой руководителя. Персональные данные в репозиторий не попадают.
  3. Прогнать кандидатов с одинаковыми параметрами генерации и схемой ответа.
  4. Посчитать согласие с руководителем по каждому критерию. Мера согласия - каппа Коэна: она учитывает совпадения, которые случились бы и наугад.

Каппа считается по двум числам: доле совпадений и доле совпадений, ожидаемых наугад. Пример с условными числами:

каппа = (совпало - совпало бы наугад) / (1 - совпало бы наугад)
модель и руководитель совпали в 90% звонков, наугад совпали бы в 60%:
каппа = (0,90 - 0,60) / (1 - 0,60) = 0,75

Из расчёта видно, что 90% совпадений дают каппу 0,75: часть совпадений случилась бы и без модели.

  1. Замерить скорость на профиле звонка (раздел 10).
  2. Взять самую маленькую модель, которая прошла порог качества.

Подробно оценка качества, трейсы и метрики разобраны в лекции «Стек LLM», разделы «Оценка качества» и «Трейсы и метрики».

ВыводДля чек-листа бери модель, которая чаще совпадает с руководителем и помещается в железо.

Приведённые измерения относятся к конфигурации и дате из списка источников. На другой версии результат может отличаться. Тексты примеров синтетические.

Очередь Ollama. Отправь четыре запроса одновременно и посмотри, когда закончится каждый. 
import asyncio, time
from openai import AsyncOpenAI

client = AsyncOpenAI(base_url="http://localhost:11434/v1", api_key="ollama")

async def ask(i, t0):
    resp = await client.chat.completions.create(
        model="qwen3.5:4b", temperature=0, seed=i, reasoning_effort="none", max_tokens=100,
        messages=[{"role": "user", "content": f"Напиши 5 предложений о видеокартах, вариант {i}."}])
    return round(time.time() - t0, 1)                 # когда закончился этот запрос

async def main():
    t0 = time.time()
    print(await asyncio.gather(*(ask(i, t0) for i in range(4))))   # четыре запроса разом

asyncio.run(main())
[4.0, 7.8, 11.7, 15.6]
Запросы закончились по очереди с шагом 4 секунды: Ollama по умолчанию обслуживает один запрос на модель (разделы 03 и 05). Попробуй перезапустить Ollama с OLLAMA_NUM_PARALLEL=4 и сравни; результат этого опыта лекция не приводит, его сделаешь сам.
Ответ по схеме. Возьми код раздела 09 и запусти его на qwen3.5:4b. Затем убери response_format и сравни, насколько свободнее станет ответ.Ответ со схемой из раздела 09 получен на Mac из примера 14.10.2026 за 7,2 с, включая загрузку модели.
Молчаливое обрезание контекста. Отправь текст на 13 тыс. токенов из 600 пронумерованных реплик с вопросом «какой номер у первой реплики?». Сначала с num_ctx 2048, потом с 16384. Через OpenAI API контекст не задать, поэтому запрос идёт в собственный API Ollama. 
import json, urllib.request

text = "\n".join(f"{i} [оператор] Реплика номер {i} о доставке заказа." for i in range(600))
for num_ctx in (2048, 16384):
    body = {"model": "qwen3.5:4b", "stream": False, "think": False,
            "options": {"num_ctx": num_ctx, "temperature": 0},     # окно контекста
            "prompt": text + "\nКакой номер у первой реплики? Ответь числом."}
    req = urllib.request.Request("http://localhost:11434/api/generate",
                                 data=json.dumps(body).encode(), headers={"Content-Type": "application/json"})
    r = json.load(urllib.request.urlopen(req))
    print(num_ctx, r["prompt_eval_count"], r["response"].strip())  # сколько прочитано и ответ
2048 1026 0554
16384 13006 0
Вывод на Mac из примера 14.10.2026: окно, прочитанные токены, ответ. При окне 2048 Ollama оставила только конец текста и не выдала ошибки, а модель уверенно назвала первой реплику 554. При окне 16384 модель прочитала все 13 006 токенов и ответила верно. Поле prompt_eval_count в ответе API (usage.prompt_tokens в OpenAI API) показывает, сколько токенов модель реально прочитала. Проверяй его в коде.
