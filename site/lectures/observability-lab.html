Наблюдаемость: от сигнала к причине

Как логи, метрики и трассировки помогают понять работу сервиса. Разберём сбор сигналов, хранилища, запросы и тревоги на условных примерах.

Учебная версия для публичной библиотеки. Рабочие сведения исключены, примеры обобщены. Версии и измерения сохранены на дату исходной лекции.

01 · ТЕОРИЯ

Зачем: мониторинг и наблюдаемость

ВыводМониторинг отвечает на заранее известные вопросы. Наблюдаемость позволяет задать новый вопрос, не меняя код.

Что такое мониторинг

Мониторинг (monitoring) - это сбор, обработка и показ числовых данных о системе в реальном времени1. Проще говоря, ты заранее решаешь, на что смотреть: загрузка процессора, место на диске, число ошибок. Система каждые несколько секунд записывает эти числа, рисует графики и шлёт тревогу, когда число выходит за порог.

Что такое наблюдаемость

Наблюдаемость (observability) - это свойство системы, при котором по её внешним данным можно понять, что происходит внутри. Данные - это логи, метрики и трассировки. Мониторинг ловит известную беду: «диск заполнен на 90%». Наблюдаемость нужна, когда беда новая: «почему учебный сервис вчера в 03:10 не ответил лиду». Ответ ищется запросом к уже собранным данным, а не новой правкой кода.

Белый и чёрный ящик

Мониторинг белого ящика (white-box) смотрит на внутренние данные системы: логи, счётчики, метрики процесса. Мониторинг чёрного ящика (black-box) проверяет поведение снаружи, как его видит пользователь1. Проверка HTTP-ответа снаружи - пример чёрного ящика. Метрики процесса - пример белого.

02 · ТЕОРИЯ

Сигналы: логи, метрики, трассировки

ВыводМетрика говорит «что-то не так», лог говорит «что именно», трассировка говорит «где в цепочке». Дешевле всего метрики, дороже всего логи.

Сигнал (signal) - это вид телеметрии, который система отдаёт наружу. OpenTelemetry выделяет три основных сигнала: трассировки, метрики и логи5.

Лог

Лог (log) - это запись о событии со временем и текстом5. Сервис пишет строку в stdout, Docker передаёт её в журнал хоста. У учебный сервис строка - JSON с полями time, level, msg и номерами сделки. Лог отвечает на вопрос «что произошло с этим лидом», но занимает много места: каждая строка хранится целиком.

{"time":"…","level":"INFO","msg":"…","case_id":…,"request_id":…}

Уровень ошибки можно извлечь из поля JSON при запросе.

Метрика

Метрика (metric) - это число, измеренное во время работы5. Сборщик берёт его раз в 15-60 секунд и хранит ряд «время - значение». Ряд называется временным рядом (time series). Метрика отвечает на вопросы «сколько» и «как быстро растёт». Хранится дёшево: Prometheus тратит в среднем 1-2 байта на одно значение7.

node_filesystem_avail_bytes{host="node-a", mountpoint="/"}  1.15e+11

Из строки видно: у метрики есть имя, метки в фигурных скобках и значение. Здесь свободно около 107 ГБ корневого диска в условном примере.

Трассировка

Трассировка (trace) - это путь одного запроса через систему5. Она состоит из отрезков (span): «принял сообщение», «спросил модель», «записал в CRM», у каждого есть начало и длительность. Трассировка отвечает на вопрос «на каком шаге ушли 40 секунд». Чтобы она появилась, код сервиса должен её отдавать через библиотеку OpenTelemetry.

СигналОтвечает на вопросЦена храненияЧто нужно от сервиса
Метрикасколько, как часто, тренднизкая байты на точкуэкспортер или счётчики в коде

03 · ТЕОРИЯ

Как устроено: сбор, хранилище, запрос, графики, тревоги

ВыводЛюбой стек наблюдаемости - это пять звеньев. Меняются только программы в звеньях и направление сбора: pull или push.

Конвейер телеметрии (telemetry pipeline) - это цепочка программ от источника данных до человека. Сборщик забирает данные у сервиса и хоста. Хранилище кладёт их на диск и чистит старое. Язык запросов достаёт нужное. Графический интерфейс рисует доски. Модуль тревог раз в минуту выполняет запрос и шлёт уведомление, если условие выполнено (рис. 1).

Как читать

  1. Слева источники. Сервис пишет строки в stdout, хост отдаёт счётчики экспортеру.
  2. Сборщик в середине - единственная программа на узле. Он толкает (push) логи и метрики в два хранилища.
  3. Grafana не хранит данных. Она отправляет запрос в хранилище и рисует ответ.
  4. Правило тревоги выполняет тот же запрос по расписанию и шлёт сообщение в Telegram.
  5. Пунктир внизу - второй способ сбора метрик: хранилище само ходит к экспортеру (pull).

Если хранилище не может обращаться к источнику по сети, подходит отправка данных от сборщика.

Pull и push

Pull - это способ сбора, при котором хранилище само опрашивает источник по HTTP. Так работает Prometheus: раз в интервал он делает запрос к адресу /metrics. Документация Prometheus называет плюсы pull: можно поднять ещё один экземпляр для проверки и легко понять, что цель недоступна6. Push - это способ, при котором источник сам отправляет данные в хранилище. Его выбирают, когда хранилище не видит источник по сети.

Читать: Prometheus FAQ, «Why do you pull rather than push?»6.

04 · ТЕОРИЯ

Инструменты

ВыводДля небольшой системы хватает Alloy, Loki, Grafana и одного хранилища метрик. Tempo и OpenTelemetry - когда сервисы начнут отдавать трассировки.

Prometheus и экспортеры

Prometheus - это база временных рядов, которая сама собирает метрики по модели pull6. Экспортер (exporter) - это маленькая программа, которая переводит чужие счётчики в формат Prometheus. node_exporter отдаёт метрики Linux с префиксом node_ на порту 91008. cAdvisor отдаёт метрики контейнеров: процессор, память, сеть27. Для логов Prometheus не подходит, документация прямо советует Loki6.

Loki

Loki - это хранилище логов, которое индексирует только метки, а не текст строк42. Строки сжимаются кусками (chunk) и лежат на диске. Поиск по тексту идёт перебором внутри выбранных метками потоков. Поэтому Loki дешёвый, но медленный на запросах без хороших меток.

Alloy

Alloy - это сборщик телеметрии от Grafana Labs, сборка OpenTelemetry Collector со встроенными конвейерами Prometheus15. Он собирает логи, метрики, трассировки и профили одной программой. Старый сборщик логов Promtail закрыт 02.03.2026, Grafana предлагает переходить на Alloy14.

Grafana, Tempo, OpenTelemetry

Grafana - это интерфейс для запросов, досок и тревог поверх любых хранилищ. Tempo - хранилище трассировок, ему нужно только объектное хранилище33. OpenTelemetry - открытый стандарт и набор библиотек, через которые код сервиса отдаёт все три сигнала по протоколу OTLP5.

Таблица 3 - инструменты, назначение и когда их брать.

Zabbix и стек LGTM: разные участки

Zabbix - это система мониторинга серверов. Агент на каждом узле снимает показатели, сервер Zabbix сравнивает их с порогами (триггерами) и шлёт тревогу3643. Сильная сторона Zabbix - железо и операционная система: диск, память, процессор, сеть, опрос устройств по SNMP и IPMI45. Логи Zabbix не хранит и не ищет: агент следит за строками в файле и шлёт тревогу на совпадение44. Трассировок в Zabbix нет.

05 · ТЕОРИЯ

Практика индустрии: LGTM, USE, RED, SLO, тревоги

ВыводХост проверяем по USE, сервис по RED, тревогу ставим на симптом, который видит пользователь.

Стек LGTM

LGTM - это набор Grafana Labs: Loki для логов, Grafana для интерфейса, Tempo для трассировок, Mimir для метрик37. Mimir - масштабируемое хранилище, совместимое с Prometheus. На одном узле вместо Mimir ставят обычный Prometheus или VictoriaMetrics.

Метод USE для ресурсов

USE - это метод проверки ресурса: «для каждого ресурса проверь использование, насыщение и ошибки»3. Использование (utilization) - доля времени, когда ресурс занят. Насыщение (saturation) - очередь работы, которую ресурс не успевает сделать. Ошибки (errors) - число отказов. Ресурсы - процессор, память, диск, сеть.

Метод RED для сервисов

RED - это метод проверки сервиса: частота запросов (rate), число ошибок (errors) и длительность (duration)4. Его предложил Том Уилки в 2015 году, потому что USE плохо подходит к сервисам. Четыре золотых сигнала Google - то же самое плюс насыщение41.

МетодДля чегоВопросыУсловный пример
USEхост и его ресурсызанят ли, есть ли очередь, есть ли ошибкизаполнение диска, swap, OOM в журнале ядра
REDсервиссколько запросов, сколько ошибок, как долгостроки учебный сервис в минуту, строки с level="ERROR"
Золотые сигналысервис для пользователязадержка, трафик, ошибки, насыщението же плюс очередь отправок

Таблица 5 - методы и что они спрашивают.

SLI, SLO и бюджет ошибок

SLI (Service Level Indicator) - это измеряемый показатель сервиса, например доля успешных ответов. SLO (Service Level Objective) - это цель для SLI: «99% запросов быстрее 100 мс»2. SLA - договор с последствиями за промах. Бюджет ошибок (error budget) - допустимая доля промахов: при SLO 99% за 30 дней это около 7 часов плохой работы. Пока бюджет не потрачен, можно спокойно выпускать релизы.

Правила хорошей тревоги

Тревога будит человека, поэтому каждая должна требовать действия1. Тревогу ставят на симптом, а не на причину: «лиды не получают ответ», а не «процессор 80%». Причина ищется уже по доскам и логам. Например, тревоги можно разделить: Аварии - нужно действие сейчас, Предупреждения - сегодня, Журнал - действия не нужно.

Читать: Brendan Gregg, The USE Method3; Grafana Labs, The RED Method4; Google SRE Book, Service Level Objectives2.

06 · ТЕОРИЯ

Настройка: Alloy, метки, запросы, доски, хранение

ВыводКонфиг Alloy - граф компонентов. Меток мало и только с конечным числом значений. Доски и конфиги живут в git.

Конфиг Alloy

Конфиг Alloy - это набор компонентов, соединённых ссылками. Компонент - блок вида тип "имя" { ... }. Один компонент читает данные, другой меняет метки, третий отправляет. Связь задаёт аргумент forward_to: он указывает, кому передать записи. Ниже минимальный пример: прочитать журнал и отправить в Loki1617.

loki.source.journal "host" {                    // читает journald хоста
  labels     = {host = "node-a", job = "journal"} // метки на каждую запись
  forward_to = [loki.write.node_b.receiver]       // передаёт записи дальше
}

loki.write "node_b" {                             // отправляет в Loki
  endpoint {
    url = "https://logs.example.org/loki/api/v1/push"
  }
}

Из примера видно: имя компонента node_b используется в ссылке loki.write.node_b.receiver. Поля журнала приходят во внутренних метках с префиксом __journal_, например __journal__systemd_unit16. Всё с префиксом __ до Loki не доходит. Поэтому нужные поля переносят в обычные метки правилами relabel.

Метки и кардинальность

Поток (stream) в Loki - это все строки с одинаковым набором меток. Кардинальность (cardinality) - число разных потоков. Если метка принимает тысячи значений, Loki строит огромный индекс и пишет тысячи мелких кусков, и запросы тормозят12. Хорошая метка описывает источник: узел, тип сбора, сервис, уровень. Плохая метка описывает событие: номер сделки, IP, id трассировки.

Таблица 6 - примеры меток, включая service, и одна плохая метка для сравнения.

LogQL

LogQL - это язык запросов Loki. Запрос начинается с селектора потоков в фигурных скобках, дальше идёт конвейер через |9. Фильтр строк |= оставляет строки с подстрокой, |~ - с регулярным выражением. Парсер | json разбирает строку в поля. Если строка не JSON, парсер ставит метку __error__, а не выбрасывает строку11. Функция count_over_time превращает строки в число за окно10.

{host="node-a", service="sales-bot"}                          # все строки условного сервиса
{host="node-a", service="sales-bot"} |= "amo"                 # только строки с подстрокой
{host="node-a", service="sales-bot"} | json | level="ERROR"   # ошибки из поля JSON
sum by (service) (count_over_time({host="node-a"}[5m]))           # строк за 5 минут по сервисам

PromQL

PromQL - это язык запросов Prometheus. Селектор выбирает ряды по имени и меткам, функция rate считает скорость роста счётчика в секунду за окно8. Счётчик (counter) только растёт, поэтому сам по себе бесполезен: смотрят на его скорость.

rate(node_cpu_seconds_total{mode="system"}[1m])     # доля процессора на ядро в режиме system
node_filesystem_avail_bytes{mountpoint="/"}         # свободно на корневом диске, байт
rate(node_network_receive_bytes_total[1m])          # входящий трафик, байт в секунду

Доски как код

Доска (dashboard) в Grafana - это JSON-документ с панелями и запросами. Провижининг (provisioning) - загрузка досок из файлов на сервере Grafana28. Если доска загружена из файла с allowUiUpdates: false, сохранить правку из интерфейса нельзя. Например, JSON доски можно хранить в git и импортировать в Grafana.

Срок хранения

Срок хранения (retention) - сколько дней хранилище держит данные. В Loki старое удаляет только компактор (compactor), и по умолчанию эта функция выключена: логи живут вечно13. Например, retention_period: 720h задаёт срок 30 дней. Prometheus по умолчанию хранит 15 дней, VictoriaMetrics - 31 день734.

Читать: LogQL9; Loki, Cardinality12; Prometheus, node exporter guide8.
