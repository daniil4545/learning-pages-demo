OpenViking изнутри: от спайка к системе

OpenViking - это сервер памяти для агентов: он принимает документы и разговоры, хранит их деревом адресов и отдаёт агенту по смыслу. Здесь мы собираем его заново, по одному механизму за шаг.

Лекция «OpenViking: полный обзор» показывает систему снаружи, через разделы Studio. Эта лекция смотрит внутрь, в код сервера и плагина Claude Code. Мы начинаем со спайка (spike), минимальной программы из десяти строк, которая ищет текст по смыслу. Затем добавляем слои по одному. Для каждого слоя разбираем, какая проблема его потребовала, что он даёт, сколько стоит и какой модуль репозитория его реализует. В конце получится схема того, как OpenViking работает сейчас, и карта мест, где наши сбои касаются кода. Читать можно подряд или с любого слоя; перед разбором некоторых слоёв есть вопрос, на который стоит ответить самому.

00

Цель и сквозной пример

Цель: после лекции ты можешь назвать путь данных от команды ov add-resource до ответа агенту и указать модуль, который отвечает за каждый шаг. Это нужно, чтобы находить причину сбоя в коде и предлагать исправления в проект.

Сквозной пример - заметка queue-pause.md на 9 КБ: разбор того, как поставить очередь OpenViking на паузу. Мы кладём её в базу, а потом агент в новой сессии спрашивает: «как остановить обработку очереди, не выключая поиск?». На каждом слое смотрим, что происходит с этой заметкой и с этим вопросом.

01

Слой 0. Спайк: текст, вектор, ближайший сосед

Задача

Вопрос «как остановить обработку очереди» и заметка про паузу могут не иметь ни одного общего слова. Поиск по строке (grep) их не свяжет. Нужен поиск по смыслу.

Механизм

Эмбеддинг (embedding) - это список из сотен чисел, который модель строит по тексту так, что близкие по смыслу тексты получают близкие списки. Спайк хранит пары «текст, вектор». На запрос он строит вектор вопроса и возвращает тексты с наибольшим косинусным сходством (cosine similarity), то есть с наименьшим углом между векторами.

docs = {}                                  # id: (текст, вектор)

def add(doc_id, text):
    docs[doc_id] = (text, embed(text))     # один вызов модели эмбеддинга

def find(query, k=3):
    v = embed(query)
    return sorted(docs, key=lambda i: -cos(v, docs[i][1]))[:k]

В OpenViking эту роль играют модели в openviking/models/embedder/ (OpenAI-совместимые, Ollama, Volcengine, Jina, локальные) и векторный индекс openviking/storage/vectordb/ на движке C++ из каталога src/1.

Граница

Спайк работает на десятках заметок. Дальше всплывают четыре проблемы: у текста нет адреса, длинный документ сжимается в один вектор и теряет детали, вызов модели на каждый документ медленный, а агент сам никогда не вызовет find. Каждый следующий слой закрывает одну из них.

02

Слой 1. Дерево адресов viking://

Задача

Агенту мало получить текст: ему нужно сослаться на него, прочитать соседние файлы, посмотреть список, найти строку. Для этого у каждой единицы нужен постоянный адрес.

Механизм

Viking URI - это адрес вида viking://resources/notes/queue-pause.md. Дерево делится на области: resources (документы), user (память, сессии и скиллы пользователя), agent (скиллы агента) и служебные temp, queue, upload3. Под адресами лежит виртуальная файловая система VikingFS: модуль openviking/storage/viking_fs/ поверх RAGFS, написанной на Rust (crates/ragfs). RAGFS умеет хранить данные на локальном диске, в S3 или в памяти4.

Поэтому у OpenViking два хранилища: файлы с полным содержимым и векторный индекс. Запись индекса - это карточка: адрес uri, уровень level (0 - .abstract.md каталога, 1 - .overview.md, 2 - сам файл), тип, вектор, короткий текст abstract, метки и права доступа16. Отдельного поля родителя в схеме кода нет, хотя документация его ещё упоминает: связь с деревом даёт сам uri с типом path, по которому можно отбирать записи по префиксу416. Поиск находит карточку по вектору, а полный текст читается из файловой системы.

Результат и цена

Агент получает команды ls, tree, read, grep, glob, которые работают без векторов. Цена в том, что два хранилища надо держать согласованными: удалённый файл должен уйти и из индекса.

03

Слой 2. Разбор и нарезка

Задача

Документы приходят в виде PDF, HTML, Markdown, кода, архивов. Один вектор на 9 КБ текста усредняет все темы заметки, и вопрос про одну деталь попадает хуже.

Механизм

Парсер (parser) - это модуль, который превращает файл одного формата в дерево разделов. Парсеры лежат в openviking/parse/parsers/, сборка дерева - в parse/tree_builder.py, весь путь приёма ресурса - в utils/resource_processor.py. Markdown режется по заголовкам, а слишком длинный раздел делится по лимиту max_section_chars в символах; старый параметр max_section_size на 2048 помечен устаревшим10.

Наша заметка становится каталогом: каждый раздел «Конфигурация воркеров», «Обходной путь», «Проверка на копии» - отдельный файл со своим адресом внутри.

Цена

Векторов становится больше, и каждый требует вызова модели. Если раздел всё равно длиннее окна модели эмбеддинга, вызов падает. Мы видели это у себя: одна задача из 813 упала с ответом 400 на слишком длинном куске.

04

Слой 3. Асинхронная очередь

Сначала подумай: заметку загрузили, команда вернула success, а поиск её не находит. Почему?

Команда только поставила задачи в очередь. Вектор и сводки ещё не построены, поэтому в индексе заметки пока нет.

Задача

Эмбеддинг и сводки - это сетевые вызовы моделей, иногда минуты на документ. Если add-resource ждёт их все, клиент отваливается по таймауту, а сервер не может принять следующую работу.

Механизм

Очередь (queue) - это список задач, который сервер разбирает в фоне. У OpenViking восемь именованных очередей: Embedding, Semantic, AddResource, Reindex, SessionCommit, ExternalParse, ExternalTask, DataCleanup. У каждой свой рабочий поток и свой предел параллельности: по умолчанию 10 для эмбеддинга, 32 для сводок, 4 для приёма ресурсов10. Хранится всё в SQLite-файле _system/queue/queue.db.

Задача проходит путь enqueue, pending, dequeue, processing, ack, removed. Подтверждение (ack) снимает задачу только после успешной обработки, поэтому при падении сервера задача не теряется. Очередь пуста, только когда и pending, и processing равны нулю: раньше проект ошибался именно здесь и считал очередь пустой, пока последняя задача ещё работала6.

Цена

Появляется окно, когда данные загружены, но не найдены. Паузы очереди нет ни в нашей версии 0.5.0, ни в main: поиск по коду не нашёл такого режима, а max_concurrent=0 не проходит проверку конфигурации. Мы обходили это копией базы без очереди для поиска.

05

Слой 4. Сводки L0 и L1

Задача

Агент нашёл десять кусков, но не знает, какой из каталогов про что. Читать все файлы целиком дорого по токенам. Нужна короткая карта каждого каталога.

Механизм

У каждого каталога есть два файла-спутника. L0 (.abstract.md) - аннотация до 256 знаков для векторного поиска и быстрого отсева. L1 (.overview.md) - обзор до 4000 знаков для переранжирования и навигации. L2 - сами файлы. У обычного файла собственных L0 и L1 нет: сводки файлов входят в L1 его каталога5.

Сводки строит storage/queuefs/semantic_processor.py снизу вверх. Сначала модель кратко описывает каждый файл, затем пишет обзор каталога из этих описаний, затем L0 вырезается из L1. После этого каталог и файлы уходят в очередь Embedding, и только тогда заметка находится поиском11.

Цена

Каждый каталог - вызов языковой модели (VLM в терминах проекта). У нас обзоры строил Codex по одному за раз: 225 каталогов шли около трёх с половиной часов. Язык сводки модель выбирает сама, и мы видели русскую карточку с обзором на португальском.

06

Слой 5. Поиск: find, search, grep

Задача

Короткий вопрос плохо выражает намерение, а десяток похожих кусков надо упорядочить.

Механизм

КомандаЧто делаетМодель
findодин векторный запростолько эмбеддинг
searchанализ намерения по контексту сессии, ноль или несколько типизированных запросовэмбеддинг и языковая модель
grep, globпо содержимому и именам в VikingFSнет

Ранжирует класс HierarchicalRetriever. Несмотря на имя, он делает один глобальный векторный поиск и, если настроен реранкер (reranker), переупорядочивает верхние результаты. Обход дерева с очередями по каталогам и раундами сходимости из кода удалён712. Иерархия сохраняется по-другому: L0 каталогов лежат в индексе как обычные записи, и поиск может вернуть каталог целиком.

ВыводИмя класса описывает старую идею, код описывает текущую. При спорах о поведении верить коду и документу 07-retrieval.md.
07

Слой 6. Сессии и долговременная память

Задача

Документы кто-то кладёт руками, а решения и предпочтения рождаются в разговоре и теряются с концом сессии.

Механизм

Сессия (session) - это журнал сообщений разговора на сервере, viking://user/.../sessions/<id>. Коммит сессии (commit) проходит в две фазы. Сначала сервер под блокировкой пути архивирует накопленные сообщения и ставит задачу в очередь SessionCommit. Затем фоновый обработчик пишет сводку архива и запускает извлечение памяти8.

Извлечение делает session/memory/extract_loop.py: языковая модель читает архив и правит файлы памяти через инструменты, по схемам типов (события, сущности, предпочтения, опыт) из system_assets/memory. Новые факты сливаются с существующими правками, а не дописываются копиями9.

Цена

Каждый коммит - вызов модели с большим выводом. Плагин Claude Code поэтому коммитит не каждую реплику, а по порогу в 20 000 накопленных токенов, который считает сам13.

08

Слой 7. Плагин и автоподсказка

Сначала подумай: агент ни разу не вызвал find, но в его контексте появились факты из памяти. Кто их туда положил?

Хук плагина на событии UserPromptSubmit: он сам ищет по тексту твоего сообщения и подмешивает блок в контекст до того, как модель начнёт отвечать.

Задача

Модель редко сама решает поискать в памяти или сохранить разговор. Значит, это должен делать код вокруг неё.

Механизм

Хук (hook) - это скрипт, который Claude Code запускает на событии. Плагин examples/claude-code-memory-plugin вешает шесть хуков13:

Stopпосле ответа отправляет новые реплики в сессию OpenViking
UserPromptSubmitищет по сообщению и подмешивает блок памяти
SessionStartподкладывает профиль
PreCompact, SessionEndсохраняют хвост перед сжатием и в конце
PreToolUseпроверяет адреса viking:// в вызовах инструментов

Блок подсказки собирает сервер: retrieve/context_assembler с квотами по типам памяти (по умолчанию 10 событий, 10 сущностей, 3 предпочтения, 0 опыта) и штрафом записям чужих проектов14. Плагин настраивает фильтры: RECALL_PEER_SCOPE (все проекты или только текущий), RECALL_EXCLUDE_URIS (поддеревья, которые не подсказывать) и RECALL_MAX_TOKENS (бюджет блока).

Цена

Каждое сообщение несёт блок в сотни токенов, нужен он или нет. В нашей проверке 30 подсказок агент не использовал ни одного факта, а 86% записей были документами корпуса. Мы убрали корпус из подсказки и сузили её до текущего проекта и 400 токенов.

09

Слой 8. Люди, проекты, доступ

Один сервер обслуживает многих людей и агентов, и память одного не должна утекать к другому. Поэтому у каждого запроса есть идентичность: аккаунт (account), пользователь (user) и peer, то есть проект или агент, от имени которого пишется память. Роли ROOT, ADMIN и USER, списки доступа (ACL), ключи API и шифрование данных живут в server/identity.py, server/auth/, storage/acl.py и crypto/15. В main peer для плагинов берётся из адреса git origin, а не из текущего каталога, поэтому память разных репозиториев больше не смешивается.

Итоговая модель

Пройдём сквозной пример по схеме. Заметка queue-pause.md идёт от CLI в сервис ресурсов, разбирается на разделы и ложится в VikingFS. Её каталог встаёт в очередь Semantic, модель пишет L0 и L1, затем очередь Embedding кладёт векторы в индекс. В новой сессии хук UserPromptSubmit отправляет вопрос в search, поиск находит каталог заметки по L0, сборщик контекста урезает результат по квотам и бюджету, и блок попадает в контекст агента.

12

Вопросы для возвращения

Ответь своими словами, потом открой разбор.

1. Зачем OpenViking хранит данные в двух местах?

Файлы в VikingFS дают адреса, чтение и grep; векторный индекс даёт поиск по смыслу. Индекс хранит адрес и вектор, текст читается из файлов.

2. Что значит «очередь пуста»?

И pending, и processing равны нулю. Пустой pending при задаче в обработке ещё не конец.

3. Для чего нужен L0 и почему его нет у отдельного файла?

L0 - короткая аннотация каталога для векторного поиска. Сводки файлов входят в L1 каталога, отдельных спутников у файлов нет.

4. Чем find отличается от search?

find делает один векторный запрос без языковой модели. search сначала анализирует намерение по контексту сессии и может сделать несколько типизированных запросов.

5. Почему плагин коммитит сессию не на каждой реплике?

Коммит запускает извлечение памяти языковой моделью. Порог в 20 000 токенов собирает материал и экономит вызовы.

6. Новый пример: ты загрузил 50 PDF, и через час поиск находит только половину. Где смотреть?

В очереди: сколько задач в pending и processing у Semantic и Embedding, нет ли ошибок задач. Половина, скорее всего, ждёт сводок или упала на эмбеддинге.
